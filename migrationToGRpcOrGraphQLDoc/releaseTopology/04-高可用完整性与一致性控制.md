# 04 · 高可用、完整性与一致性控制

> **部署硬约束**：未来 RTD 测试网/正式网全部必需中间件均须自建开源，包括 MinIO、Apache HBase/HDFS/ZooKeeper、PostgreSQL、RocksDB，以及数据库高可用与备份、密钥/证书、网络入口、指标日志告警和镜像仓库。上游 Bigtable/AWS 或其它闭源云服务文档仅用于理解原始语义，不能成为生产运行依赖。见[开源适配方案](./03-远程检查点归档存储与Ledger-gRPC.md)和[开源中间件政策](../../../rtd-archive-service/OPEN_SOURCE_POLICY.md)。

本文把“有进程”“有水位”“有备份”“查询正确”拆成不同验收事实。以下标有**建议新增控制**的机制是 RTD 生产运维方案，不能误认为 `temp/rtd` 已经原生提供。现有标准组件及搭建方法见 [02](./02-通用索引GraphQL与Consistent-Store.md)、[03](./03-远程检查点归档存储与Ledger-gRPC.md)。官方说明了[索引器逐管线 watermarks](https://docs.sui.io/operators/data-management/indexer-stack-setup)、[归档多地域独立部署和备份](https://docs.sui.io/operators/data-management/archival-stack-setup)、[归档响应的信任边界](https://docs.sui.io/develop/accessing-data/archival-store/what-is-archival-store)。

## 1. 不可妥协的数据不变量

| 编号          | 必须成立的事实                                                                                                                                                        | 生产验证与阻断动作                                                                                                                                                                                                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I1 同链       | 源 checkpoint 0 的 digest、Full Node `GetServiceInfo.chain_id`、对象桶、PG 每条 pipeline、HBase 每条 pipeline 与 GraphQL 所连后端属于**同一创世链**。环境名相同不够。 | 部署前读取并比对完整链 ID；不一致禁止启动写入和跨源查询。Alt [存储链 ID 检查](../../../temp/rtd/crates/rtd-indexer-alt-framework/src/pipeline/processor.rs#L116-L134)与 HBase 适配后保留的 [CAS 绑定](../../../temp/rtd/crates/rtd-kvstore/src/bigtable/client/mod.rs#L571-L606)是第二道防线。                    |
| I2 原始连续   | 对承诺从创世提供的服务，checkpoint 必须从 0 到已发布最高序号连续，且摘要链、内容、交易和对象集合可验证。                                                              | **建议新增控制**：独立审计器维护 `verifiedThrough`，逐段重读原始桶，验证相邻序号，并按协议区分创世特殊规则与后续 checkpoint 的可信委员会认证 summary；发现缺口或不一致冻结发布水位，保留故障原件，不用调大起点掩盖。验证器须直接基于同版 `temp/rtd` 的类型、proto 和委员会语义新建，不使用旧 `rtd-indexer` 实现。 |
| I3 持久后公布 | 写入对象、数据库记录与可读性复核在前，服务可宣称的连续水位在后；发生部分提交不得把“已摄取”当“已归档”。                                                                | 比较对象桶确认文件、解码、摘要、PG/HBase 记录和各管线已提交 watermark；随机重读及边界全量比对。标准远程桶水位文件是写入进度，**本身不是**链证书或用户查询完整性的证明。[本地 reader](../../../temp/rtd/crates/rtd-indexer-alt-framework/src/ingestion/store_client.rs#L26-L30)。                                  |
| I4 分层覆盖   | 原始桶、HBase Ledger、PG 各管线、Consistent Store 各有不同的有效范围；读路由只可在请求所需数据的**交集**内宣称成功。                                                  | 记录 `H_raw_verified`、`H_hbase(p)`、`H_pg(p)`、`H_cs(p)`、`L_pg(p)` 和 Full Node 最新/最低可用序号。查询需要的有效上界是相关管线的最低已提交上界；不能拿最快管线水位代表整体。                                                                                                                                   |
| I5 修剪安全   | Full Node 修剪旧 checkpoint 前，原始桶已完成认证、连续、持久化与独立可恢复性检查；需要旧数据查询的 PG/HBase 仍可从完整桶补洞。                                        | 设 `source_lowest_available` 与 `H_raw_verified` 的安全余量门槛；若归档落后或备份失败，暂停/放宽节点修剪、切换未修剪来源或停止对外完整历史承诺。节点保留开关见[本地配置](../../../temp/rtd/crates/rtd-config/src/node.rs#L1325-L1443)。                                                                           |
| I6 不伪造缺失 | 当链 ID、覆盖、水位或后端健康未知时，旧交易/对象的 `NOT_FOUND` 不能解释成“链上不存在”；服务故障也不能转成空列表。                                                     | 上层查询/BFF 对“无数据”“尚未索引”“已修剪”“归档不可用”建不同状态；未知广播不得重签或重播，使用原 digest 查询。[官方迁移说明](https://docs.sui.io/develop/accessing-data/json-rpc-migration)。                                                                                                                      |
| I7 可恢复     | “有备份”须通过隔离环境中从原始桶、PG PITR、HBase 快照与 HDFS 备份、RocksDB 形式化快照分别恢复并比对完成证明。                                                         | 按故障演练记录 RPO/RTO、恢复后的链 ID、连续水位、抽样对象/交易/事件，以及读写切换结果；备份失败进入上线阻断。                                                                                                                                                                                                     |

`H_*` 是本方案建议维护的**运维覆盖模型**，不是某个标准二进制已提供的同名 API。官方 PostgreSQL 以 `watermarks` 表按 pipeline 跟踪 `checkpoint_hi_inclusive`，`reader_lo` 和修剪下界必须一并看。[官方排障说明](https://docs.sui.io/operators/data-management/indexer-stack-setup)。归档 [`GetServiceInfo` 实现](../../../temp/rtd/crates/rtd-kv-rpc/src/v2/mod.rs#L192-L216)给出若干点查管线的最低上界，但其 `lowest_available_checkpoint` 当前写成 0；所以**不能据此自动证明从 0 到上界的历史覆盖**。必须完成从 0 回填和实际旧样本核验。[归档默认参与的八条管线](../../../temp/rtd/crates/rtd-kv-rpc/src/lib.rs#L60-L72)。

I2/I3 的验证水位**不能只靠同桶的 JSON 文件强制**：已在 dev 观察到标准 PG Alt 越过该文件记录的 1755，从同桶对象摄取到 1873。生产须在自建 MinIO 上隔离暂存与已验证发布桶，并以不同身份/策略确保所有索引器只读发布桶；验证/发布器先核对连续性和版本摘要，再复制不可变文件。公开查询仍按各层已核验覆盖交集放行。只增加一个 `verifiedThrough` 数字、却让索引器继续读取暂存桶，不能算 I2/I3 通过。[详细边界](./03-远程检查点归档存储与Ledger-gRPC.md#2-原始-checkpoint生产-minio)。

## 2. 五个数据层的高可用形态

| 层                 | 建议拓扑                                                                                                                                                | 故障恢复与一致性要点                                                                                                                                                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Full Node          | 至少两个不同故障域的同链独立节点，经 gRPC 入口做健康路由；执行路径另设容量与限流。                                                                      | 按节点 `GetServiceInfo`、checkpoint 最新/最低水位和只读模拟做常规探测；真实执行只在隔离测试网或受控专用账号做低频端到端演练，未知广播保留原 digest 重查，不把真交易当负载均衡健康探针；不跨链负载均衡。Full Node 落后时可停止实时/执行服务，历史归档仍可读至已覆盖水位。                |
| 原始 checkpoint 桶 | 对 `{seq}.binpb.zst` 启用版本化、不可改写保留及跨故障域副本；对会更新的 `epochs.json`/水位文件保留受控条件写权限。writer 多实例前验证同键内容冲突处理。 | 官方称 2–3 个 tip writer 可利用幂等写入，但 RTD 仍应验同序号内容相同、故障切换无洞。[官方远程桶指南](https://docs.sui.io/operators/data-management/remote-store-setup)。桶权限/生命周期不得清除从创世开始的事实文件。                                                                   |
| HBase 归档         | 每地域自建 HBase/HDFS/ZooKeeper 独立集群，配套各自 `rtd-kvstore-alt` 写入器与多个只读 `rtd-kv-rpc`；中间网关只在私网开放并校验服务身份。                | HBase 原生快照和 HDFS 备份需在隔离环境恢复 14 表，逐表核对同链身份、实际覆盖和 `watermark_alt`；错时快照不得冒充跨表原子快照。故障时从可信 MinIO 原始桶按已提交水位补洞，必要时从 0 重建；第二地域追平并样本比对后方可切流。[HBase 架构](https://hbase.apache.org/docs/architecture/)。 |
| PostgreSQL Alt     | 高可用主库+可提升备库、WAL/PITR、异地备份；每个 pipeline 有单写入归属/受框架控制的并发，GraphQL 横向多副本。                                            | 不直接从滞后只读副本宣称最新索引；先对齐每条管线已提交水位。数据库切换后读取水位并抽样比对，必要时从原始桶重放，而不是手工伪造水位。                                                                                                                                                    |
| Consistent Store   | 每个实例独立持久 SSD/RocksDB 路径；可有各自同步的备用实例，经健康和水位路由。                                                                           | 一个 RocksDB 路径只允许一个进程打开。新实例由同链形式化快照或 checkpoint 0 重建，不能空库从中途开始；四条 pipeline 追平后才接受近期余额/持有对象查询。[官方 Consistent Store 指南](https://docs.sui.io/operators/data-management/indexer-stack-setup)。                                 |

GraphQL 本身可多副本，必须把数据库、归档、Consistent Store 和 Full Node 的依赖健康加入发布/路由条件。进程 HTTP `/health` 只是一种探测；`rtd-kv-rpc` 的 [health handler](../../../temp/rtd/crates/rtd-kv-rpc/src/main.rs#L170-L172)固定回 `OK`，**不检查** HBase、链 ID、数据覆盖或落后。需要外部合成查询与水位门槛，不得把 `/health=200` 等同于归档就绪。官方 GraphQL 健康页能展示索引 lag，但也要用真实查询检查详情、筛选、当前余额与执行。[官方 GraphQL 与水位排障](https://docs.sui.io/operators/data-management/indexer-stack-setup)。

## 3. 正确的读语义和跨层一致性

1. **固定查询边界**：对于同一页面需要交易列表、详情和余额的情况，选择 RTD 目标 checkpoint `H_query`，使它不高于相关 PG 管线、归档点查和 Consistent Store 的共同可读上界。请求显式使用 GraphQL 可用的 checkpoint/游标边界；无法在同一边界上服务时返回“数据同步中”，不能拼接出看似同一时刻的跨层结果。官方说明 GraphQL/Consistent Store 使用 checkpoint 固定保证快照语义，[架构页](https://docs.sui.io/develop/accessing-data/graphql/graphql-rpc)。具体字段和游标语义须以锁定版本 schema 集成测试为准。
2. **名单与详情分层**：在标准 GraphQL 路径中，PG 负责“哪些 digest/版本符合筛选”，归档 Ledger 负责“这个 digest/版本的原始详情”；若单独选用 Ledger `List*`，其受支持过滤走 HBase bitmap 管线，须另验覆盖、性能和客户端路由。如果 PG 可筛出 digest 但归档未覆盖，应暴露依赖滞后；不能静默删掉该列表项。历史筛选需求的保留期由对应 PG pipeline 决定；HBase 长期点查不自动补足已修剪的地址/事件索引。[官方管线职责](https://docs.sui.io/develop/accessing-data/graphql/graphql-rpc)。
3. **负结果要有覆盖前提**：对于已知 checkpoint 的键，只有确认同链、完整来源、请求落在数据覆盖范围内且服务已健康读取时，`NOT_FOUND` 才接近“该键在该覆盖范围不存在”。对于未知 digest，没有完整的 digest→checkpoint 索引或其他存在性证明，仅凭 Full Node `NOT_FOUND` 不足以得出链上不存在。归档不可用应保留为可重试/不可用错误。此为建议的 BFF/网关语义，标准 LedgerService 不会自动提供完整“缺失证明”。
4. **禁止隐式跨源降级**：Full Node 查询超出保留期，应显式转到归档端点；归档失败不得回到同样已修剪的节点无限重试。JSON-RPC 原先的隐式历史回退不能作为 gRPC 的行为假设。[官方历史查询说明](https://docs.sui.io/develop/accessing-data/archival-store/using-archival-store)。

## 4. 写入来源与验证深度

官方远程 checkpoint writer 和 indexer framework 可以写入、解码并跟踪水位；仅凭能解压、能反序列化、能从桶读取，**不能得出已经验证链上事实**。[本地对象桶读取](../../../temp/rtd/crates/rtd-indexer-alt-framework/src/ingestion/store_client.rs#L65-L123)只是获取和解码；[官方归档说明](https://docs.sui.io/develop/accessing-data/archival-store/what-is-archival-store)提醒调用方信任边界。建议在原始桶发布入口增加独立验收：

1. 对 checkpoint summary、序号、前序摘要、contents 摘要、交易及 effects/object 集合做与目标版本协议一致的校验；按 RTD 当前/历史委员会与 epoch 变更验证认证材料。验证范围和算法须由 `temp/rtd` 对应共识/存储实现及安全审计确认。
2. 对同一序号进行条件写入/不可覆写策略与读后比对；发现两份不同内容立即隔离，不采用“最后写入胜”。现有 [blob commit](../../../temp/rtd/crates/rtd-checkpoint-blob-indexer/src/handlers/checkpoint_blob.rs#L112-L136) 是普通 `put`，所以这项保护须新增或由经验证的存储代理强制；`epochs.json`/水位文件仍需可做受控版本更新，不能用禁止一切同键写入的整桶策略阻断正常运行。S3 Object Lock 只保护旧 VersionId，允许新版本和 delete marker；故须钉住已验证事实文件的 VersionId/digest，并监测同 key 最新视图是否变化，不能把 Object Lock 本身当防覆写闸门。[AWS 协议语义参考](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)。**RTD 生产桶只用自建 MinIO，须对它实测对应行为，不能依赖 AWS 服务。**
3. 维护独立、连续的“已验证且已在至少两个故障域持久化”水位，并保存验证清单/版本。此机制是**建议新增控制面**；如果只运行上游标准栈，不应对外宣称此水位已存在。
4. 每日抽样历史、每次升级/灾备恢复全检边界和最近窗口；以同链第二节点/第二地域独立源交叉核对摘要。把“数据桶可读”“解码成功”“链事实可信”“数据库查询完整”分别记录。

上述验证、上传、哈希回读与连续发布控制需在新 `rtd-archive-service` 中实现，不引入旧 `rtd-indexer` 运行时；标准来源保持 `.binpb.zst`。[格式说明](https://docs.sui.io/operators/data-management/remote-store-setup)。

## 5. 监控、告警与故障动作

| 信号                                                                           | 需要区分的故障                     | 首要动作                                                                                                                                         |
| ------------------------------------------------------------------------------ | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Full Node head - H_raw_verified` 及 `Full Node lowest_available`              | 原始 writer 停滞、节点修剪逼近     | 停止扩大修剪风险，切备用节点/恢复 writer；若源已丢失，隔离并从可信备份补回，不跳序号。                                                           |
| 原始桶序号/哈希/摘要冲突                                                       | 存储损坏、串链、错误覆写或恶意数据 | 冻结可发布水位与下游回填，保存两个版本，查源并恢复；不能自动接受“较新版本”。                                                                     |
| 各 PG/HBase/Consistent pipeline 的 `checkpoint_hi_inclusive`、`reader_lo`、lag | 某一管线停滞、修剪越界、数据库瓶颈 | 按上游下载、处理、提交三段定位；相关 GraphQL 查询不再宣称新水位。[官方排障](https://docs.sui.io/operators/data-management/indexer-stack-setup)。 |
| Ledger `GetServiceInfo`、旧样本 `Get*`、HBase 读错误                           | `/health` 正常但归档不可用或不完整 | 摘除归档副本，保留未知状态；切到已验收同链第二地域，不用空结果代替失败。                                                                         |
| GraphQL 查询 p95/p99、复杂度拒绝、分页游标与跨源详情缺失                       | 高负载、PG 修剪过早、归档落后      | 限制请求成本、扩读副本/后端，必要时缩小对外历史窗口并明确反馈。                                                                                  |
| 恢复点年龄、备份副本数、定期恢复结果                                           | 只有“备份任务成功”但不能恢复       | 阻断修剪策略扩大与上线门槛，修复备份，执行隔离恢复演练。                                                                                         |

SLO 的具体分钟数、保留期、RPO 和 RTO 需根据 RTD 流量、成本与业务承诺设定并压测，不照搬 Sui 主网数值。最低硬门槛是：**不把未验证的 checkpoint 或管线水位宣传为完整，不把故障和修剪误报为链上不存在，且任何保留承诺都有可恢复的原始数据来源。**
