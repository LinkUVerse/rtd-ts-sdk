# 07 · RTD 归档统一服务：工程、单机与生产环境

决策基准：2026-09-24；当前锁定源码基线 `temp/rtd` 的 `dc1ea13a66`（原始决策基线 `269e9a4a09`）。本文件描述要建设的系统，不能代替构建、实际链数据验收或故障演练。功能职责沿用 [01](./01-决策总览与源码映射.md) 至 [04](./04-高可用完整性与一致性控制.md)。[Sui 官方通用索引/GraphQL 手册](https://docs.sui.io/operators/data-management/indexer-stack-setup)、[远程 checkpoint 手册](https://docs.sui.io/operators/data-management/remote-store-setup)、[Bigtable 归档手册](https://docs.sui.io/operators/data-management/archival-stack-setup)为技术依据；所有来源、链 ID 和数据都是 RTD 自有。

## 1. 实施边界与 monorepo

**高优先级约束：所有 RTD 测试网和未来正式网中间件必须可自建且开源，不依赖 Google Cloud Bigtable、GCS、AWS S3、Azure Blob 或闭源托管服务。** `rtd-archive-service` 是 **构建与运维 monorepo**，记录同一 `temp/rtd` 提交、同一 `rtd-apis` 协议版本、镜像摘要和配置。六个标准 Rust 可执行文件都由 `temp/rtd` 对应源码构建；这里按组件分工程目录，集中管理命令、配置、镜像和环境部署，不复制旧 `rtd-indexer` 实现。`rtd-node` Full Node 仍由主链部署，作为这个数据栈的必需外部依赖；它不能由归档服务替代。

云对象桶、Bigtable、托管数据库、云密钥管理、闭源网络入口、镜像仓库和监控的替换及发布闸门统一按[开源中间件政策](../../../rtd-archive-service/OPEN_SOURCE_POLICY.md)执行；S3 只是协议，内部 Bigtable v2 protobuf 只是兼容合同，均不得引入对应云服务运行依赖。生产建设选型还包括自建 Patroni/etcd 与 pgBackRest、OpenBao/cert-manager、Envoy、Prometheus/Alertmanager/OpenTelemetry Collector 和 Harbor 开源版；这些支撑组件均**尚未部署或验收**，不得从设计表推断已具备高可用。

这个硬约束也适用于作为外部依赖的 `rtd-node` Full Node/验证节点及其快照、状态同步路径，以及未来可能部署的分析任务。锁定源码已让主链共用对象存储、旧版恢复和分析输出拒绝 GCS/Azure、隐式 AWS 端点与云元数据凭据回退，并删除 Snowflake 监控及 AWS KMS CLI；[全局源码审计](../../../rtd-archive-service/CLOUD_DEPENDENCY_AUDIT.md#归档六组件之外的全局残留)记录逐路径状态。正式部署仍须在自建 MinIO 上实测主链恢复，并以实际配置、隔离网络、DNS/出站和故障恢复证明；六组件的开发证据不能外推为整个 RTD 生态生产通过。

| 子工程                                     | 标准二进制                         | 状态源/依赖                                     | 服务出口                                   |
| ------------------------------------------ | ---------------------------------- | ----------------------------------------------- | ------------------------------------------ |
| `modules/checkpoint-blob`                  | `rtd-checkpoint-blob-indexer`      | Full Node gRPC → RTD 专属 checkpoint 桶         | `.binpb.zst`、`epochs.json`                |
| `modules/indexer-alt`                      | `rtd-indexer-alt`                  | 完整桶/Full Node → PostgreSQL                   | PG pipelines、watermarks                   |
| `modules/consistent-store`                 | `rtd-indexer-alt-consistent-store` | 完整桶/Full Node → 每副本独立 RocksDB           | 当前对象/余额 gRPC                         |
| `modules/kvstore-alt`                      | `rtd-kvstore-alt`                  | 完整桶/Full Node → HBase 兼容网关 → HBase 14 表 | 归档数据和逐管线水位                       |
| `modules/kv-rpc`                           | `rtd-kv-rpc`                       | HBase 兼容网关与自建 HBase                      | 历史 Ledger gRPC                           |
| `modules/graphql`                          | `rtd-indexer-alt-graphql`          | PG、Ledger、Consistent Store、Full Node         | 对应用的 GraphQL                           |

所有构建都锁定 `temp/rtd` Git SHA、Cargo.lock 和工具链，构建证明与镜像 digest 随发布归档。源路径不一致则 fail closed；不能悄悄改用旧 `rtd` 或 Sui 上游二进制。部署时记录 RTD 创世 digest 与期望 chain ID；**空 PG/HBase 首次写入前**必须通过外部身份门禁，库内首次绑定的自检不足以防止写错空库。[身份不变量](./04-高可用完整性与一致性控制.md#1-不可妥协的数据不变量)。

## 2. dev：Docker Compose 与单机运维

`localDeploy/compose.yaml` 负责 PostgreSQL、开源 S3 本地服务、单节点 HBase Master/RegionServer + 独立 ZooKeeper 和初始化容器；如监控 UI 需要指标时再加 Prometheus。服务的配置和启动脚本同放 `localDeploy`，可选择本机已经构建的 RTD 二进制或同源码镜像。容器只在宿主回环地址暴露调试口；无密钥写入 Git。当前 MinIO 镜像只提供开发 S3 合同测试；其社区仓库已归档，生产原始桶必须改为 RTD 维护源码 fork 自建的分布式 MinIO，且须完成补丁、许可证、版本化、复制与恢复验收。dev 的 HBase 共享本地卷只用于开发，生产要有自建 HDFS/ZooKeeper/多 RegionServer。dev 重建历史库后，必须从保留的原始 checkpoint 桶从 0 回填。

原上游客户端固定连接 Google Bigtable；当前 [`rtd-kvstore-alt`](../../../temp/rtd/crates/rtd-kvstore/src/bin/rtd-kvstore-alt.rs) 和 [`rtd-kv-rpc`](../../../temp/rtd/crates/rtd-kv-rpc/src/lib.rs) 调用的 [`new_remote`](../../../temp/rtd/crates/rtd-kvstore/src/bigtable/client/mod.rs) 已改成显式连接 RTD 自建 HBase 网关。私网网关已实现当前客户端的 Bigtable v2 读、写、条件变更和流式响应；开发环境的连接拒绝、协议与 mTLS 合同、独立 RTD 链 0–100 的 14 表回填及 HBase 清空后重建均已通过。自建 MinIO、生产 HDFS HA 和多故障域恢复仍须验证。[适配合同](./03-远程检查点归档存储与Ledger-gRPC.md#3-hbase-适配网关必须开发与验证)。

启动次序：启动中间件并等健康 → 空 HBase 实例建 14 表/列族 `rtd`、PG 初始化和**隔离的暂存/发布桶** → 校验创世链身份及源 checkpoint 0 → blob writer 仅写暂存桶 → 独立验证并将连续事实发布到索引器专用只读桶 → Alt/Consistent Store/KVStore 从发布桶回填 → KV RPC → GraphQL → 管理控制面。同桶写额外验证水位文件不能替代物理隔离：dev 已观察到标准 PG Alt 越过文件中的 1755 摄取同桶 checkpoint 到 1873。开发 MinIO 已通过 0–100 的双桶/独立读者局部合同，且官方 PG Alt 的临时库只从发布桶摄取到 100；**生产 MinIO 发布器、持久账本及 HBase/RocksDB 等全部索引器切桶仍待建设**。[边界与证据](./03-远程检查点归档存储与Ledger-gRPC.md#2-原始-checkpoint生产-minio)。崩溃重启不能清理 PG 或原始桶；PG、MinIO、HBase 与 RocksDB 从各自已提交水位续跑。**HBase 历史库若重建，要隔离 KV RPC 旧查询并从完整桶重新回填**，不能凭一个旧 watermark 宣称数据仍在。切换到 Full Node 追 tip 只在回填追平、旧数据查询和连续性核验通过后进行。`localDeploy` 脚本需要 `up`、`down`（保留持久数据）、`status`、`logs`、`verify` 和显式危险的 `reset-dev-data`；普通启动和故障恢复不调用 reset。

## 3. 测试网/未来正式网：Kubernetes 与状态服务

正式环境用**每网络独立命名空间、独立资源和数据域**；任何 public endpoint 均由实际 RTD 域名和证书配置，不能编造可用公网服务。Kubernetes 控制面与 etcd 也须由 RTD 自建；它管理无状态工作负载、故障域分散、重启和单活接管。有状态中间件必须用自建、开源且经过故障演练的 HA 集群或开源 Operator。Kubernetes Deployment 的 2 个副本本身不等于 PG、HBase/HDFS/ZooKeeper、MinIO 或 RocksDB 的 HA。

| 服务             | 推荐编排                                                              | 失效/接管边界                                                                                                                  |
| ---------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Full Node        | 主链团队至少两个独立故障域的同链节点                                  | 健康路由须校验 chain ID、最新/最低 checkpoint；执行不转给归档                                                                  |
| Blob writer      | 回填单活；追 tip 多副本前先通过同序号冲突保护验证                     | 所有 writer 指向同链桶；对象冲突停止发布；跨区副本和恢复演练                                                                   |
| Alt PG 管线组    | 每组只给一个活跃 writer，`Recreate`/受控单活接管；不同组可并行        | 不能盲目同组多写。旧 Pod 彻底停止或有经验证的 fencing 后，新 Pod 从 PG watermark 续跑；PG 故障期间保留源、失败重试与可观测告警 |
| Consistent Store | 至少两个各自有独立 PVC/RocksDB 的副本；客户端只路由已追平者           | 每个副本独立从源补追；跨节点调度，不能共享同一 RocksDB 路径                                                                    |
| KVStore Alt      | 对同一 14 管线组先单活；跨区域独立 HBase/HDFS/ZooKeeper 集群和 writer | 从 HBase 已提交水位续跑；HBase/HDFS 故障时停止宣称新历史覆盖，恢复后自动重试/接管并从 RTD 完整桶补洞                           |
| KV RPC / GraphQL | 至少 2 副本、反亲和与 PDB、按数据就绪门槛路由                         | `/health` 或 TCP 存活不足以证明历史可用；探针要做旧样本与水位合成查询                                                          |
| PostgreSQL       | 自建 PostgreSQL + Patroni/etcd、pgBackRest WAL/PITR                   | 故障切换后审计每管线已提交水位、索引表和 chain ID；恢复性证据由演练给出                                                        |
| 原始桶/HBase     | 对象版本与跨区副本；HBase 每地域独立集群                              | 14 表快照须验证跨表恢复边界；恢复后逐表验水位及重放；不能只看 `watermark_alt`                                                  |

密钥与证书使用自建 OpenBao、私有 CA 和 cert-manager；OpenBao 不能把云 KMS 当作必需的解封服务。公共 gRPC/GraphQL 入口用自建 Envoy 实施认证、流量限制和健康路由；观测用自建 Prometheus/Alertmanager、OpenTelemetry Collector 及经许可审计的开源日志后端；镜像放自建 Harbor 开源版。它们不是可选的闭源 SaaS 替代开关：任一必需环节尚未部署、备份和故障恢复验收时，生产放行条件仍不满足。具体版本和许可证在 A6 发布清单中锁定。

生产策略必须包含 Pod 资源 requests/limits、反亲和或 topology spread、PDB、滚动升级上限、只读与写入身份分离、开源工作负载身份/证书体系、NetworkPolicy、TLS、Secret 引用、日志/指标/追踪、配置和镜像不可变摘要。**单活并不保证“零秒不中断写入”**：故障时允许有界索引滞后，但受控重启或接管后必须从水位连续补齐，读层不能把滞后报为链上不存在。多节点故障能力必须在真实独立故障域和已演练的中间件 HA 上验证，不靠副本数推断。

生产默认让回填/续跑始终使用 RTD 自有全保留远程桶；追 tip 可用 Full Node polling/streaming。发生 Full Node 修剪窗口外的停机时，必须回桶补洞，不能跳水位继续。对 PG/HBase 恢复，先独立验证 chain ID、完整序号和每条水位，再重新开放查询。故障恢复目标和告警阈值按 RTD 测试网实测给出，文档不填虚构 RPO/RTO。

## 4. 管理监控页与受控操作

`web-admin` 显示网络身份、各服务版本/镜像、Full Node head 和修剪下界、原始桶连续已验证水位、PG 每条 `checkpoint_hi_inclusive`/`reader_lo`、HBase 14 管线水位、Consistent Store 四管线、GraphQL 与 Ledger 真实查询、实例健康与复制/备份状态。各项明确标注**已采集、不可用、未核验、已验证**，不能把 Prometheus 上报或 `/health=200` 展示成历史完整。

`control-api` 从 PG 只读查询与标准组件指标/探针采集事实；新增的验证事实用独立控制库保存，不回写官方水位。手动操作限定为：重新执行只读核验、触发备份/恢复演练、对指定管线创建受范围限制的回填 Job、暂停/恢复单活写入组、触发安全的重新索引流程。每个操作必须有身份认证、最小 RBAC、CSRF/会话保护、目标网络与区间预览、幂等键、审计日志、作业状态和超时；删除数据、改水位、重置创世不能由普通页面直接执行。重索引须采用影子库/影子表或经过审批的停写事务，不允许只删 watermark。[官方重新索引说明](https://docs.sui.io/operators/data-management/indexer-stack-setup)。管理端只在内网或受身份代理保护的入口开放，不与公开 GraphQL 共域共享管理员令牌。

## 5. 完成定义与钱包前置门槛

单机验收至少要证明：从 RTD checkpoint 0 到选定有界高度产生真实 `.binpb.zst`；HBase 14 表和 PG/Consistent 的标准管线都提交水位；KV RPC 对旧样本返回与 Full Node/原始源一致的详情；GraphQL 查询余额、对象和交易；依次停掉 PG、HBase、开源 S3 服务、Full Node 后恢复，每层从断点继续且不重置数据；管理页面如实显示故障并可触发有审计的运维任务。生产验收另需多故障域节点故障、PG 切主、HBase/HDFS/ZooKeeper 独立地域、MinIO 桶副本、全套备份恢复与链身份冲突测试。[原验收矩阵](./06-上线顺序与验收演练.md)。

只有上述归档统一服务模块完成并在目标 dev RTD 链上通过端到端验收，才按 [前端审计](../02-RTD-SDK与前端现状审计.md)开始钱包 JSON-RPC 迁移。地址 `0xc535…bf0df9` 是 32 字节十六进制地址，**不是 BIP-39 助记词**；钱包真实导入与 Chrome 扩展测试需要能导出该地址的有效助记词或私钥，以及明确的本地测试链身份。不能把地址字符串作为秘密材料导入，也不能凭构建成功声称浏览器验收通过。
